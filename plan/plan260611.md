# 本次更新计划：Feedback-Driven Prefix Tree Planner

## 核心思路

本次计划不再把重点放在固定语义分类上，也不再让本地小模型主要承担 `team_policy`、`tool_policy`、`output_format` 这类细粒度分类任务。

新的核心目标是：

> 将 Agent prompt 编译成可操作的 block 序列，由 planner 直接学习如何重排和构建 prefix tree；validator 保留必要硬约束，并根据 cache 命中与任务 utility 的综合反馈决定接受或回滚，从而逐步优化 planner 的排序策略。

也就是说，系统从原来的：

```text
Compiler -> Semantic Classifier -> Planner -> Validator
```

调整为：

```text
Compiler -> Planner -> Validator -> Feedback Learner -> Planner
```

固定类别只作为可选解释信息，不再作为核心决策依据。真正用于决策的是：

- block 是否能被安全移动；
- block 是否能和其他请求形成共享前缀；
- 重排后 cache 命中率是否提升；
- 重排后任务 utility 是否保持或提升；
- 历史反馈是否证明某类排序策略有效。

## 模块划分

### 1. Compiler：直接分块

Compiler 的职责是把原始 Agent prompt 分成可重排的 block。

第一版可以让本地小模型直接辅助分块，而不是先用规则进行细分类。Compiler 输出的重点不是“这个块属于哪个固定类别”，而是保留后续 planner 需要的信息：

- block 边界；
- block 原始顺序；
- block 文本或安全 hash；
- block 所属 message / agent / source；
- block 是否疑似包含硬风险；
- block 与前后文的依赖关系；
- 可选的简短 natural language summary。

Compiler 可以输出少量辅助 metadata，但这些 metadata 不作为最终排序规则，只作为 planner 和 validator 的参考。

### 2. Planner：直接排序和构树

Planner 的职责是给定一批 blocks，直接生成新的 block 顺序或 prefix tree。

Planner 不再先依赖固定分类再排序，而是直接优化：

```text
maximize expected_cache_gain
subject to hard_constraints and utility_preservation
```

Planner 需要考虑：

- 哪些 block 应该放到全局共享前缀；
- 哪些 block 应该成为部分 Agent 的子组共享前缀；
- 哪些 block 应留在 agent-local suffix；
- 哪些 block 不值得移动；
- 哪些已有历史排序策略在类似任务上表现更好。

后续可以把 planner 训练成一个本地小模型或策略模型，使其根据历史反馈动态调整排序。

### 3. Validator：硬约束 + Utility 判断

Validator 分成两层：

```text
Hard Constraint Gate -> Utility Preservation Check
```

第一层是已有 validator 需要保留的硬约束检查。第二层是本次后续要补的 utility 判断，用来回答：

> 这个通过硬约束的重排，是否大概率保持了任务效果？

本次暂不训练 utility 小模型，先把接口和人工标注样例框架搭好。

硬约束用于防止明显危险或不可恢复的重排。只要违反硬约束，直接回滚，不进入 utility 比较。

需要保留的硬约束包括：

- block 不能丢失、不能篡改、不能错误重复；
- tools、tool choice、model args 等调用参数不能被重排过程改变；
- 最新用户指令不能被放入稳定共享前缀；
- 私有记忆、密钥、credential、私有配置不能共享；
- 私有工具权限不能被提升成全局共享内容；
- agent role identity 不能被错误提升成 global shared prefix；
- tool result、代码执行结果、外部环境观测结果不能乱序；
- conversation history 不能在没有明确允许的情况下破坏时序；
- 重排后的 prompt 必须能被解释、记录和回滚；
- telemetry / summary 默认不能记录 prompt 正文或密钥。

通过硬约束后，Validator 再进入 utility 判断。

后续目标是用一个本地小模型判断：

```json
{
  "is_utility_preserved": true,
  "confidence": 0.0,
  "reason": "short_reason"
}
```

但当前阶段不训练这个模型，也不把模型判断接入主流程。本次只做：

- 预留 utility validator 的输入 / 输出结构；
- 基于 HumanEval 构造少量本地人工标注样例；
- 用这些样例描述“什么样的合法重排会保持 utility，什么样的合法重排可能伤害 utility”；
- 后续再讨论是否训练小模型、如何训练、如何评估。

需要强调：utility 小模型未来只判断“已经通过硬约束的候选”。它不负责识别硬约束违规样本，也不需要学习明显违法的重排。它要学习的是：

> 合法但可能让任务效果变差的重排。

通过 utility 判断后，不再计算包含 task utility 的综合分数。Utility 在这里作为 gate，只输出是否保持任务效果：

```text
is_utility_preserved = true / false
```

如果 `is_utility_preserved=false`，直接回滚，并把失败反馈给 Planner。

只有 `is_utility_preserved=true` 的候选才进入 cache benefit 判断。Cache benefit 第一版不做复杂打分，只判断重排后是否提升了可命中的共享前缀：

```text
cache_hit_increased = true / false
```

如果 utility preserved 且 cache hit increased，则接受该重排；否则回滚。

后续如果有真实 provider telemetry，可以把 `cache_hit_increased` 从离线估计替换为真实指标，例如 cached tokens 是否增加、cache hit ratio 是否提升。

### 4. Feedback Learner：用反馈优化 Planner

Feedback Learner 记录每次重排尝试的结果，用于更新 planner 的排序策略。

反馈来源包括：

- 是否通过硬约束；
- 是否实际应用重排；
- cache 命中率变化；
- cached tokens 变化；
- latency 变化；
- cost 变化；
- task success / score 变化；
- semantic guard 或人工复核结果；
- fallback reason；
- 哪些 block placement 经常成功；
- 哪些 block placement 经常失败。

长期目标是让系统“用得越久，排序越准”：

- 常成功的 block placement 被强化；
- 常失败的 block placement 被降低权重；
- 原本不合理的 group 可以拆分；
- 长期等价且安全的 group 可以合并；
- planner 逐步学会针对不同任务、不同 Agent 结构生成更优 prefix tree。

**一些问题**

1. feedback learner直接训练小模型；
2. planner 输出是prefix tree。



## utility的模型训练路径

## Utility 判断与 Cache 命中

本节明确：本次不设计连续型 task utility 分数。Utility 只作为 0/1 gate。

```text
Hard Constraint Gate
    -> Utility Preservation Gate
    -> Cache Hit Increased Gate
    -> Accept / Rollback
```

### Utility Preservation Gate

Utility Preservation Gate 的目标是判断：

> 通过硬约束的重排，是否保持了任务效果？

长期路线使用一个本地小模型判断：

```json
{
  "is_utility_preserved": true,
  "confidence": 0.0,
  "reason": "short_reason"
}
```

如果未来能找到可靠的直接 oracle，例如 HumanEval 单元测试结果，也可以用 oracle 给训练数据或评估数据打标签。

当前阶段暂不训练模型，也不把模型接入主流程。本次先做 HumanEval 本地人工标注小样例，用来为后续 `LocalUtilityValidator` 训练或评估提供基础。

### 人工标注样例来源

基于当前仓库里的 HumanEval 测试集和多 Agent 模板：

- `datasets/HumanEval/`
- TwoAgents scenario
- GroupChatThreeAgents scenario

对每个样例保存：

- original prompt blocks；
- reordered prompt blocks；
- moved block summary；
- 是否通过硬约束；
- 人工标注的 `is_utility_preserved`；
- 标注理由；
- 可选的 HumanEval task id / scenario id。

### 标注重点

人工标注不要覆盖硬约束违规样本。硬约束违规样本已经由 validator 第一层处理。

人工标注重点关注：

- 通过硬约束，但角色约束位置变化后可能影响解题行为；
- 通过硬约束，但输出格式约束移动后可能影响测试结果；
- 通过硬约束，但工具使用说明移动后可能影响代码生成 / 验证；
- 通过硬约束，但任务背景和 agent-specific 指令顺序变化后可能影响协作；
- 保守重排后看起来仍保持原始任务语义的正例。

### 其他问题

- `LocalUtilityValidator` 的输入是整段重排后发给云端的请求，但是不是http，是他的前一步，也就是这个插件所在的位置。
- `LocalUtilityValidator` 输出 0/1之后，同时输出 confidence；
- cache hit increased 用我根目录下面那个cache-hit-proxy做本地估计。

### 暂留问题

后续需要确定：

- 如何用 HumanEval oracle 或人工标注构造训练 / 验证这个validator的模型；
- 如何把 utility gate 和 cache hit gate 的结果反馈给 planner，来让这个planner排序的更准。

## 初步验收标准

本次设计落地后，应满足：

- 新计划清楚表达系统从固定语义分类转向反馈驱动排序；
- 保留必要硬约束，不把所有风险都交给 utility 事后判断；
- 明确 utility 计算方法仍待讨论；
